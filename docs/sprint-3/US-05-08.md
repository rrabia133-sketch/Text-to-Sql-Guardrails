## Story Narratives

### US-05 — Schema-Grounded Context & Business Glossary
> **As an analyst**,  
> **I want** generated SQL queries to be strictly grounded in the approved database schema and standardized business definitions,  
> **So that** generated queries only reference real, permitted database objects and adhere to verified metric calculations without hallucinations.

### US-06 — Natural Language to SQL Generation & Bounded Retries
> **As an analyst**,  
> **I want** to ask questions in plain English and receive schema-valid PostgreSQL query previews with structured assumptions,  
> **So that** I can explore analytical data without writing SQL manually, while knowing invalid outputs are rejected and retried with bounded safety.

### US-07 — Clarification Flow & Ambiguity Handling
> **As an analyst**,  
> **I want** the system to ask for clarification when my question is ambiguous, underspecified, or missing critical business parameters,  
> **So that** the model does not guess my intent or invent arbitrary calculations behind my back.

### US-08 — Provider Routing, Local-Only Enforcement & Budget Ledger
> **As an administrator**,  
> **I want** strict policy routing between local Ollama and approved Groq models, with an enforced local-only airgap mode and daily cloud budget ledger,  
> **So that** sensitive queries never leave the local environment unless approved, and cloud API spend is strictly capped and audited.

## Acceptance Criteria

### US-05 Acceptance Criteria
- [x] **AC-US05-1 (Schema Allowlist Enforcement):** Context presented to generation models includes only approved tables (`customers`, `products`, `orders`, `order_items`), safe columns, and established foreign key relationships. Hidden columns, internal IDs, and PostgreSQL system catalogs (`pg_*`, `information_schema`) are stripped from context.
- [x] **AC-US05-2 (Versioned Business Glossary):** Core business metrics (e.g. `revenue`, `completed_order`, `active_customer`, `average_order_value`) are maintained in a versioned registry (`GLOSSARY_VERSION`); exact SQL expressions and join requirements are passed into model grounding.
- [x] **AC-US05-3 (Deterministic Date Resolution):** Relative date terms (e.g. "last month", "yesterday", "YTD", "Q3 2026") resolve to deterministic ISO-8601 start and end timestamps against a configured application timezone (`ANALYTICS_TIMEZONE`, default `UTC`).
- [x] **AC-US05-4 (Grounding Transparency):** The active schema version, glossary version, and resolved date bounds are returned in API responses and visible to analysts in the UI preview panel.

### US-06 Acceptance Criteria
- [x] **AC-US06-1 (Structured Response Contract):** Both Ollama and Groq adapters return structured JSON matching a strict schema containing `sql`, `assumptions`, `referenced_tables`, `referenced_columns`, and `explanation`.
- [x] **AC-US06-2 (Input Validation & Request Caps):** Natural-language questions are limited to a maximum length (e.g. 500 characters); empty questions, whitespace-only, or oversized inputs are rejected with descriptive validation errors before invoking any LLM.
- [x] **AC-US06-3 (Bounded Generation Retries):** If an LLM returns malformed JSON, markdown fences, or syntactically invalid SQL, the system performs at most ONE automatic regeneration attempt passing the error diagnostic back to the model. Continued failure fails closed.
- [x] **AC-US06-4 (Query Artifact Persistence without Execution):** Generation outputs are persisted in `app_db` as owned `query_artifacts` with status `preview`; absolutely NO database execution against `analytics_db` occurs during Sprint 3.

### US-07 Acceptance Criteria
- [x] **AC-US07-1 (Ambiguity Detection):** Questions lacking essential metrics (e.g. "Who are our best customers?" without specifying revenue vs. order frequency) or missing date ranges trigger a structured clarification response rather than guessing.
- [x] **AC-US07-2 (Structured Clarification DTO):** Clarification responses provide a clear question, structured options, and reason code (`status: "clarification"`).
- [x] **AC-US07-3 (Clarified Question Follow-up):** Submitting a clarification response links to the original query context and initiates a clean generation cycle producing a new immutable query artifact.
- [x] **AC-US07-4 (Abstention on Unsupported Data):** Questions requesting data outside the approved schema (e.g. "Show employee salaries" or "Store inventory logs") result in immediate, explainable refusal rather than hallucinated tables.

### US-08 Acceptance Criteria
- [x] **AC-US08-1 (Local-Only Airgap Guarantee):** When configured with `PROVIDER_MODE=local`, no outbound network requests are made to Groq or any external cloud host. Ollama downtime results in a clean error and NEVER falls back silently to cloud.
- [x] **AC-US08-2 (Backend Credential Isolation):** Groq API keys and endpoint secrets are stored exclusively in backend environment configuration; neither the frontend client nor API responses ever expose provider tokens.
- [x] **AC-US08-3 (Data Minimization in Cloud Payloads):** When Groq is utilized, outbound payloads contain strictly the sanitized schema allowlist, versioned glossary rules, and the sanitized user question; no database rows, customer PII, or internal database connection strings are transmitted.
- [x] **AC-US08-4 (Daily Budget Ledger & Hard Stop):** Outbound Groq calls increment a daily token and cost ledger in `app_db`. If daily spend exceeds the configured limit (`DAILY_CLOUD_BUDGET_USD`, default $5.00), cloud generation immediately halts with an actionable `429 Too Many Requests` error.
