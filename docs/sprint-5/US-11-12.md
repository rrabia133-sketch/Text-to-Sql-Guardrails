## Story Narratives

### US-11 — Semantic Validation & Meaning Verification
> **As an analyst**,  
> **I want** generated SQL queries to undergo automated semantic validation comparing the question's extracted intent slots (metric, filters, date boundaries, join structure, and grouping) against the normalized AST and versioned business glossary,  
> **So that** queries that appear syntactically and structurally valid but compute the wrong answer (e.g. wrong aggregation function, unhandled order cancellation statuses, missing calendar bounds, or Cartesian fanout duplicates) are flagged, repaired under bounded retry, or blocked before execution.

### US-12 — Explained Confidence Scoring & Decision Bands
> **As an analyst**,  
> **I want** a transparent, explainable confidence score (0–100) detailing the exact evidence behind the generation, highlighting any missing or uncomputed components and categorizing the query into actionable decision bands (`high`, `review`, `blocked`),  
> **So that** I understand the reliability of the generated SQL, must explicitly review and acknowledge medium-confidence queries before execution, and am prevented from running low-confidence or ungrounded queries, with clear labeling that uncalibrated scores represent heuristic confidence.

## Acceptance Criteria

### US-11 Acceptance Criteria
- [ ] **AC-US11-1 (Intent Slot Extraction & Alignment):** Natural language questions are parsed into structured intent slots: metric name, aggregation type (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`), dimension grouping, filter predicates, temporal boundaries (with analytics timezone), sort direction, and requested row limits. The AST is mapped against these slots.
- [ ] **AC-US11-2 (Glossary Metric & Status Conformance):** Queries referencing domain metrics (e.g., "revenue", "sales") must strictly adhere to the business glossary definition: sum of `order_items.quantity * order_items.unit_price` restricted to completed orders (`orders.status = 'completed'`). Queries computing revenue without filtering completed orders or using raw order totals produce a `CRITICAL` semantic mismatch finding.
- [ ] **AC-US11-3 (Temporal Boundary & Timezone Integrity):** Questions specifying relative or absolute time ranges (e.g., "last month", "Q3 2024", "yesterday") must project identical ISO-8601 boundary expressions in the `WHERE` clause matching the resolved timezone bounds. Missing or skewed date filters produce a `CRITICAL` finding.
- [ ] **AC-US11-4 (Join Cardinality & Fanout Duplication Prevention):** Multi-table joins (e.g. `orders` joined to `order_items`) must guard against accidental row duplication and double-counting. If a query aggregates across a 1-to-many relationship without proper grouping or `DISTINCT`, a `WARNING` or `CRITICAL` fanout finding is generated.
- [ ] **AC-US11-5 (Bounded Automated Semantic Repair):** When repairable semantic mismatches are detected (such as missing `status = 'completed'` or incorrect aggregation function), the system attempts at most one automated repair (`maxRepairAttempts = 1`). The repaired query is completely re-run through the recursive AST visitor, normalizer, and schema validators. Repair attempts can **never** weaken security policies or bypass AST rules.
- [ ] **AC-US11-6 (Empty Result Distinguishability):** The execution and validation engine cleanly distinguishes an empty database result set (e.g., a valid query returning 0 rows because no records matched the filters) from an execution failure, query timeout, or semantic mismatch.

### US-12 Acceptance Criteria
- [ ] **AC-US12-1 (4-Component Deterministic Confidence Formula):** Confidence score is computed deterministically as an integer from 0 to 100 based on weighted component evidence:
  1. **35% Intent-Slot Agreement:** Proportion of extracted intent slots (metric, filters, time bounds, grouping, order) accurately represented in the AST.
  2. **30% Glossary, Join & Aggregation Evidence:** Adherence to official glossary formulas, valid join paths, and safe aggregation without fanout.
  3. **20% Verifier Agreement:** Structural and semantic verification consensus from deterministic AST checks and bounded verifier output.
  4. **15% Candidate Stability:** Semantic equivalence between the primary query and an independently generated secondary candidate.
- [ ] **AC-US12-2 (Explicit Unavailable Evidence Accounting):** If any score component cannot be computed (e.g., candidate generation disabled or timed out, or verifier unreachable), that component contributes **0 points** and is explicitly labeled as `unavailable: true` with a clear reason code. The score is **never** silently renormalized away to artificially inflate confidence.
- [ ] **AC-US12-3 (Decision Bands Enforcement):** Queries are classified into 3 distinct decision bands:
  - **`high` (85–100):** Eligible for execution; preview presented; requires user click on "Run Query".
  - **`review` (65–84):** Requires explicit analyst review and acknowledgement of warnings before execution is enabled. Blocked if any `CRITICAL` finding exists.
  - **`blocked` / `abstain` (< 65):** Execution is forbidden. Query preview displays explanation and asks user to refine or clarify their question.
- [ ] **AC-US12-4 (Subordination to Security Guardrails):** Confidence score is strictly subordinate to security. An artifact with a high confidence score (e.g., 95) that triggers an AST guardrail violation (e.g., non-SELECT, unapproved table, forbidden function, excessive cost) is unconditionally blocked from execution.
- [ ] **AC-US12-5 (Heuristic Labeling & Transparency):** The user interface and API response explicitly label the score as "Heuristic Confidence" with accompanying explanatory tooltips, acknowledging that the score is a structured heuristic prior to statistical calibration against real-world distributions.
- [ ] **AC-US12-6 (Development Evaluation & Abstention Tuning):** Automated benchmark evaluation on the development dataset verifies that high-confidence wrong-answer rate is ≤5%, ambiguous query refusal recall is ≥90%, and false refusal rate on supported queries is ≤15%. The holdout dataset remains strictly sequestered and untouched.
