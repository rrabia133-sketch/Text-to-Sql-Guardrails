## Story Narratives

### US-09 — Recursive AST Safety Guardrails & Scoped Validation
> **As an administrator and security auditor**,  
> **I want** generated SQL queries to undergo rigorous, recursive AST validation, scope-aware identifier resolution, normalization, and plan-cost gating before any execution can be scheduled,  
> **So that** arbitrary writes, chained queries, system catalog inspection, resource exhaustion attacks, and syntax/alias hallucinations fail closed with deterministic, explainable security findings.

### US-10 — Restricted Database Execution & Resource Containment
> **As an analyst**,  
> **I want** to execute verified, owned query previews in a tightly contained, read-only PostgreSQL execution sandbox with strict statement, lock, row, byte, and concurrency caps,  
> **So that** I receive accurate, typed analytical results without risking database degradation, lock contention, unauthorized data modification, or cross-tenant data leaks.

## Acceptance Criteria

### US-09 Acceptance Criteria
- [x] **AC-US09-1 (Single SELECT Enforcement & Multi-Statement Rejection):** Exactly one query statement is allowed. Multi-statements chained via semicolons (`;`), statement stacking, and non-`SELECT` statements (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `CREATE`, `GRANT`, `COPY`, `VACUUM`) are unconditionally rejected before database contact.
- [x] **AC-US09-2 (Recursive AST Traversal & Node Whitelisting):** AST is parsed using `pgsql-ast-parser` and inspected recursively. Any unrecognized AST node type, locking construct (`FOR UPDATE`, `FOR SHARE`), transaction control (`BEGIN`, `COMMIT`), or administrative clause triggers an immediate policy violation.
- [ ] **AC-US09-3 (Scoped Identifier & CTE Resolution):** Table aliases, Common Table Expressions (`WITH ... AS (...)`), subqueries, and join conditions are recursively resolved. References must strictly resolve to the 4 approved schema tables (`customers`, `products`, `orders`, `order_items`). Internal PostgreSQL catalogs (`pg_*`, `information_schema`) and unapproved tables/columns are blocked.
- [ ] **AC-US09-4 (Function Allowlist Enforcement):** Queries may only invoke approved scalar and aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `DATE_TRUNC`, `EXTRACT`, `COALESCE`, `ROUND`, `LOWER`, `UPPER`). Dangerous functions (`pg_sleep`, `pg_read_file`, `query_to_xml`, administrative functions, UDFs) trigger immediate rejection.
- [ ] **AC-US09-5 (Normalization & Mandatory Row-Cap Revalidation):** SQL is formatted/normalized into canonical syntax. If a `LIMIT` clause is omitted, `LIMIT 50` is injected; if present, it is bounded to a maximum of `LIMIT 100`. Any automated SQL modification or injection automatically triggers a fresh recursive validation pass over the modified AST.
- [ ] **AC-US09-6 (EXPLAIN Plan Cost Gating):** Before production execution, queries undergo a non-executing `EXPLAIN (FORMAT JSON)` inspection in a short transaction. If planner total estimated cost exceeds the threshold (`MAX_PLAN_COST`, default 10,000 units), execution is rejected to prevent denial of service.

### US-10 Acceptance Criteria
- [ ] **AC-US10-1 (Immutable Artifact Ownership & Expiry Verification):** Execution requests (`POST /api/v1/queries/:id/execute`) accept only an owned, server-stored query artifact in `preview` state. Clients cannot submit or mutate arbitrary SQL. Expired artifacts (`expires_at < NOW()`, >15 minutes old) or altered SQL hashes are denied.
- [ ] **AC-US10-2 (Restricted Execution Credentials & Kernel Containment):** Database queries execute strictly via dedicated `analytics_user` on `analytics_db` inside an explicit `BEGIN READ ONLY;` transaction. Any database write or DDL attempt is blocked by PostgreSQL kernel permissions independently of AST checks.
- [ ] **AC-US10-3 (Deterministic Execution Resource Bounds):** Queries execute under strict server-side and database-level limits: statement timeout (5,000 ms), lock timeout (1,000 ms), maximum row limit (500 rows), and maximum payload byte limit (1 MiB). Exceeding these bounds terminates query execution cleanly.
- [ ] **AC-US10-4 (Active Concurrency Throttling & Queue Management):** Execution respects strict concurrency limits: maximum 2 concurrent queries per user and maximum 10 concurrent queries globally across the instance. Overflow requests return `429 Too Many Requests` or queued rejection with actionable status.
- [ ] **AC-US10-5 (Graceful Cancellation & Connection Pool Cleanup):** Client disconnection, user cancellation (`POST /api/v1/executions/:id/cancel`), or timeout sends `pg_cancel_backend` or cancels the active transaction, executes `ROLLBACK`, and safely releases or discards the connection without leaking pool slots or socket descriptors.
- [ ] **AC-US10-6 (Audit Logging & Data Privacy):** Every execution attempt records an audit event in `app_db` containing request ID, user ID, artifact ID, execution duration, row count, status, and policy outcome. Zero result rows, raw customer PII, or database passwords are ever written to application logs.
