## Story Narratives

### US-02 — Foundation Workspace & Shared Contracts
> **As a developer**,  
> **I want** a reproducible Fastify/React workspace with shared contracts,  
> **So that** development, testing, and continuous integration checks run consistently across all environments.

### US-03 — User Identity & Session Ownership
> **As an analyst**,  
> **I want** to sign in and own my workspace session,  
> **So that** my generated queries, artifacts, execution results, and history remain private and strictly isolated from other users.

### US-04 — Approved Analytics Fixture & Database Containment
> **As an administrator**,  
> **I want** an approved synthetic analytics fixture and a separate application metadata database with strictly contained database roles,  
> **So that** users and query execution pipelines access only permitted analytical data and can never modify, escalate, or compromise database integrity.

## Acceptance Criteria

### US-02 Criteria
- [ ] **AC-US02-1 (Clean Checkout Setup):** Given a clean repository clone, executing documented setup procedure installs dependencies, connects to the database container, and starts both Fastify and React dev servers without manual workarounds.
- [ ] **AC-US02-2 (Shared Contract Validation):** Given a shared TypeScript contract package (`packages/contracts`), API request/response schemas are imported by both frontend and backend; invalid request payloads are rejected by Fastify validation before reaching route handlers.
- [ ] **AC-US02-3 (Zero Secret Commitment):** Environment configuration is validated at server boot against a strict schema; `.env.example` provides complete placeholder definitions with no secrets committed to version control.
- [ ] **AC-US02-4 (Baseline Quality Gates):** Monorepo exposes unified root npm scripts (`build`, `test`, `lint`, `typecheck`) that execute cleanly across all packages and apps in CI.

### US-03 Criteria
- [ ] **AC-US03-1 (Authentication Enforcement):** Unauthenticated requests to protected API endpoints fail immediately with `401 Unauthorized`; expired sessions require re-authentication.
- [ ] **AC-US03-2 (Session Expiry & Secure Cookies):** User sessions are managed server-side in `app_db` with secure, `httpOnly`, `SameSite=Lax` cookies or signed tokens; revoked/expired sessions are rejected.
- [ ] **AC-US03-3 (Artifact Ownership & IDOR Protection):** Analyst A cannot fetch, execute, export, or delete Analyst B's query artifacts or history by guessing resource identifiers; requests fail closed with `404 Not Found` or `403 Forbidden`.
- [ ] **AC-US03-4 (Server-Side Role Enforcement):** System roles (`analyst`, `admin`) are verified on the server in route guards; frontend role presentation cannot bypass backend authorization checks.

### US-04 Criteria
- [ ] **AC-US04-1 (Synthetic Analytics Fixture Reproducibility):** Synthetic analytics data in `analytics_db` includes nulls, ties, canceled orders, and deterministic performance records across `customers`, `products`, `orders`, and `order_items`.
- [ ] **AC-US04-2 (Strict Analytical Read-Only Execution Role):** Execution credential `analytics_user` connects exclusively to `analytics_db` with `default_transaction_read_only = on` and `statement_timeout = '5s'`; any write, temporary object creation, or schema modification is rejected at the database kernel level.
- [ ] **AC-US04-3 (Separated Application Metadata Database):** Application state (users, sessions, query logs, audit trail) is hosted in an isolated `app_db` managed by a separate role (`app_user`), preventing analytical queries from seeing or touching user metadata.
- [ ] **AC-US04-4 (Cross-Database Containment):** `analytics_user` is forbidden from connecting to or reading `app_db`, and possesses no superuser or administrative privileges.
